# CPU 파서 풀 324 구현·측정 결과

동일한 문서 14개를 처리하는 시간이 **37.47초 → 22.93초, 38.8% 단축**됐다. GPU 평균 사용률은 **34.1% → 56.9%**로 상승했다. 사용자 요청에 따라 구성별 실측은 **1회**이며, 구성별 워밍업은 별도다. 50% 단축 목표에는 도달하지 않았다. 이번 기준선의 절반은 18.74초다.

구현 커밋: `f27aeb9`, 브랜치: `perf/parser-cpu-324`. API·파서·Windows 워커 후보를 격리 환경에서 함께 시험했다. 기본 동시성은 1로 유지했고 상시 서비스에 후보를 배포하지 않았다.

## 시간과 GPU

구성 숫자는 문서 슬롯 / 파서 프로세스 / 파서 CPU 한도 순서다. CPU 한도 4는 컨테이너의 CPU 시간 할당량이며 물리 코어 4개 고정이나 모든 코어 100% 사용을 뜻하지 않는다.

| 구성 | 전체 처리 시간 | 112 대비 단축 | GPU 평균 | GPU 최대 | GPU 10% 미만 시간 추정 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 / 1 / 2 | 37.47초 | 기준선 | 34.1% | 100% | 22.57초 |
| 2 / 1 / 2 | 26.39초 | 29.6% | 48.5% | 100% | 11.92초 |
| 2 / 2 / 2 | 31.99초 | 14.6% | 39.5% | 100% | 16.62초 |
| 2 / 2 / 4 | 24.08초 | 35.7% | 53.4% | 100% | 8.74초 |
| **3 / 2 / 4** | **22.93초** | **38.8%** | **56.9%** | **100%** | **7.22초** |

다섯 실행 모두 14개 성공, 검색 가능한 벡터 885개, 문서별 청크 수 일치, 호스트·API·파서 임시 작업 파일 잔여 0이다. 실측 문서 시도는 총 70/70 성공했다. 원본 14개의 SHA-256·크기·수정 시각도 모두 유지됐다.

전체 시간은 호스트의 첫 문서 시작부터 마지막 문서의 정리·상태 ACK 완료까지다. 프로세스 기동과 제어용 상태 조회 지연은 제외했다. 특히 212의 제어 루프 관측 시간은 47.80초였지만 실제 문서 처리 구간은 26.39초다. GPU 통계도 같은 호스트 UTC 구간으로 잘랐다. 실행 명령을 누른 순간부터의 체감 대기 시간과는 구분해야 한다.

GPU는 `nvidia-smi`로 약 200ms 간격, 자원은 약 3초 간격으로 기록했다. GPU 평균은 해당 구간 표본 평균이며 장치 전체 수치다. 10% 미만 시간은 저사용 표본 비율 × 처리 시간의 근사값이다. 다른 GPU 작업의 영향을 완전히 배제하거나 GPU 커널만의 시간을 측정한 결과는 아니다.

## 부하와 병목 해석

가장 큰 잔여 병목은 **후반 HWP·PDF 두 문서의 임베딩 경로**다. HWP의 임베딩 요청 구간은 9.84초(전체 시작 후 12.95~22.79초), PDF는 9.62초(12.86~22.48초)였다. 두 구간은 겹친다. 두 문서가 전체 임베딩 단계 누계 25.18초의 77.3%를 차지하며, 해당 후반 구간 GPU 평균은 89.1%(47개 표본)였다. API 감사 기록의 UTC 시작점에 같은 프로세스의 단계 상대 시간을 더해 GPU 표본 구간을 맞췄으므로 시간축 정밀도의 한계는 있다.

같은 HWP/PDF의 파싱 HTTP 구간은 각각 1.39/4.12초였다. 따라서 후반 종료 시간을 줄이는 다음 분석 대상은 임베딩 요청 대기·토큰화·모델 추론 시간 분리다. 큰 작업의 준비를 앞당기는 순서 조정과 임베딩 배치 크기 조정도 후속 비교 후보지만, 이번에는 추가 변경이나 실행을 하지 않았다. GPU 평균 56.9%는 앞부분의 공급 공백과 후반의 높은 부하를 함께 평균 낸 값이므로 전 구간 GPU가 같은 정도로 한가하다고 해석하면 안 된다. 파서 슬롯 대기는 전체 문서 누계 0.98초여서 파서 수만 더 늘리는 것을 우선하지 않는다.

| 항목 | 112 | 324 | 해석 |
| --- | ---: | ---: | --- |
| VRAM 최대 | 4,793 MiB | 4,793 MiB | GTX 1080의 8 GiB 범위 내 |
| API 메모리 표본 최대 | 1,856.7 MiB | 2,040.4 MiB | API 한도 4 GiB |
| 파서 컨테이너 메모리 최대 | 670.3 MiB | 993.7 MiB | 직전 워밍업 포함, 한도 3 GiB |
| WSL 가용 메모리 표본 최소 | 2,990.1 MiB | 2,266.8 MiB | 호스트 총 RAM 약 15.16 GiB |
| 파서 CPU 제한 대기 누계 | 0.075초 | 0초 | cgroup throttled_usec 증가분 |
| 파서 프로세스 간 요청 중첩 | 0초 | 3.02초 | 업로드부터 정리까지 요청 구간 |

CPU는 Ryzen 5 7600(6코어/12논리 프로세서)다. 222에서는 파서 CPU 제한 대기가 0.940초 관측됐고, 224와 324에서는 0이었다. 이번 관측은 **파서 수만 늘리기보다 CPU 할당도 함께 조정해야 한다**는 판단을 뒷받침한다. 단회 비교이므로 시간 차이 전체를 CPU 제한 하나로 설명할 수는 없다.

212의 클라이언트 파서 슬롯 대기 합계는 5.35초였고, 224는 약 0초, 324는 0.98초였다. 324에서는 문서 슬롯 3개가 파서 2개를 공유하면서 일부 대기가 생겼다. 파싱과 다른 문서의 임베딩 요청 구간 중첩은 112의 0초에서 324의 2.34초로 늘었다. 이 구간에는 HTTP 전송·대기도 포함된다. 단계 시간 합계는 서로 겹치므로 전체 시간으로 더하지 않는다.

324는 224보다 1.15초(4.8%) 빨랐지만 문서별 평균 지연은 3.39초 → 4.02초, 표본 p95는 11.92초 → 14.29초였다. 묶음 처리량과 개별 문서 지연의 교환 관계가 관측됐다. 문서 14개에서 계산한 지연 분포이며 검색 응답 p95가 아니다. 이 결과만으로 슬롯을 더 늘리는 것은 권하지 않는다.

최종 비교에서 컨테이너 OOM과 정리 누락은 없었다. 기존 WSL swap 할당이 시험 전부터 약 4 GiB 있었으며, 324 표본 구간의 swap 입출력은 각각 72/52페이지였다. 이번 실행 중 큰 swap 폭증은 관측되지 않았다. OCR·대용량 묶음·검색 동시 부하는 시험하지 않아 일반적인 서비스 부하 합격을 뜻하지 않는다.

## 구현 범위

- 파서 서버에 재사용 가능한 독립 프로세스 풀 1/2를 추가했다. 업로드부터 정리까지 슬롯을 소유하고 초과 요청은 본문 버퍼링 전에 거절한다. 한 작업의 중단이 다른 작업을 종료하지 않도록 분리했다.
- 클라이언트는 API 프로세스 공통·서비스 URL별 슬롯을 직렬화 이전에 얻는다. 슬롯 대기·직렬화·응답 읽기가 하나의 제한 시간을 공유한다. 정확한 `PARSER_BUSY` 오류만 제한 시간 안에서 재시도하고, 정리 실패는 별도로 차단한다.
- API claim과 Windows 감독 프로세스에 문서 슬롯 3개를 지원했다. 슬롯별 작업·정리 경로, 부모 종료 시 자식 종료, OCR 단독 admission과 복호화 gate 1을 유지했다.
- 내용 없는 타이밍에 파서 큐·직렬화·전송·busy 대기와 서버 작업 구간을 추가했다. `parse_ms`는 워커 응답/IPC 구간이며 순수 CPU 계산 시간이 아니다.

## 시험 조건과 한계

표본은 8형식 14문서, 49,692,616바이트다. PDF 3, HWP 3, PPTX 2, XLSX 2, DOC/DOCX/XLS/HWPX 각 1개다. 문서별 청크 수 정렬값은 `[1, 2, 3, 5, 5, 10, 14, 19, 41, 63, 66, 71, 290, 295]`다. manifest SHA-256은 `d9e75e20b8c19560deadc125fd42299dd5b6bfc8997b89aadf6549f16388846f`다.

GTE 768차원, 배치 32, 전체 임베딩 요청 동시성 2, GPU 모델 추론 1, 복호화 1, API 프로세스 1을 고정했다. Kordoc OCR은 비활성화했다. SQL 스키마·ES·Redis·MinIO·API·파서는 시험 대상으로 격리했다. 순서는 112→212→222→224→324이며, 순서 효과를 상쇄하는 반복/교차 시험은 수행하지 않았다.

최종 코드 이전의 진단 실행은 표에서 제외했다. 그중 `run-1-212`에 `HOST_WORKER_ERROR` 1건이 있었다. 약 31초의 호스트 전달 단계에서 발생했고 해당 문서의 ingestion attempt 감사 기록이 시작되지 않았다. 원인은 확정하지 못했다. 최종 측정에서는 재발하지 않았지만 해결됐다고 주장하지 않는다. 최종 워커에는 실패 시 예외 종류/HResult만 남기는 시험용 진단을 추가했으며 최종 다섯 실행에 해당 실패 기록은 없었다.

실측 1회이므로 반복성·통계적 유의성·50% 단축을 주장하지 않는다. 온도, 장시간 지속 부하 및 동시 검색 지연은 별도 합격 판정 대상이다. 민감 원문·인증 설정·원시 감사 자료는 Git에 포함하지 않았다. 로컬 상세 자료는 이 worktree의 `.local/matrix-20261013`에 보존했다. 공유 가능한 수치는 [측정 JSON](measurements/cpu-parser-324-2026-10-13.json)에 기록했다.

## 검증과 리뷰 판정

- Node 39/39 통과: 프로세스 풀과 실제 LibreOffice 변환 정리 통합 시험 포함.
- Python 140/140 통과: ingestion 서비스/runtime/제한, pool claim route, Kordoc client/bridge 범위.
- Windows 풀 시험 통과: 자식 3개, 격리 경로, 공통 복호화 gate, 부모 종료 시 정리.
- 제거된 runtime 검사와 `git diff --check` 통과. 전체 저장소의 무관한 테스트를 전부 실행한 것은 아니다.
- 별도 읽기 전용 리뷰에서 확인한 중요한 두 문제(만료 업로드 버퍼 보유, 천천히 도착하는 응답의 전체 제한 시간 초과)를 재현하고 수정했다. 수정 후 위 검증을 완료했다.
- 경미한 테스트 보완 두 건은 보류했다: cap3 시험의 후보를 4개로 늘리기, 일부 변경된 cap3 시험에 cap2 매개변수 유지하기. 별도 경쟁 claim 시험이 4요청/상한3을 검사하므로 구현 차단 사항으로 보지 않았다.
- 리뷰 당시 미확인이던 성능 비교와 최종 자원 정리는 이 보고서의 결과로 보완했다. 여러 API 프로세스에 걸친 문서 admission, 상시 배포, DOCX 내장 이미지 OCR 성능은 범위 밖이다.

시험 종료 후 원본 14/14 미변경, host/API/parser 잔여 파일 0, 시험용 컨테이너와 DB 제거를 확인했다. 원래 개발 ingest 워커와 source watcher 예약 작업은 Running 상태로 복구했다. 구현 브랜치와 결과 기록은 보존한다.

## 후속 적용 시 설정

후보 API·파서·Windows 파일 묶음을 함께 적용해야 한다. 진행 중인 작업, 모든 슬롯의 receipt ACK, 파서 workspace가 비었는지 먼저 확인한다. 현재 프로세스의 limiter 용량을 작업 중 변경하지 않는다.

```text
KORDOC_WORKERS=2
KORDOC_CPUS=4
KORDOC_CLIENT_CONCURRENCY=2
DOCMIND_INGESTION_DOCUMENT_CONCURRENCY=3
Windows Start-DocMindIngestionPool.ps1: -Concurrency 3
```

후보 Compose는 `KORDOC_WORKERS`에서 API의 client concurrency도 함께 설정한다. 별도 실행 방식이라면 두 값을 직접 맞춰야 한다. 복구 시에도 모든 슬롯을 drain한 후 문서/파서/클라이언트 동시성을 1로 되돌린다. 이 설정은 적용 절차 기록이며 이번 작업에서 상시 활성화하지 않았다.
