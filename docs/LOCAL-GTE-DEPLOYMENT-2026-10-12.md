## 복구와 관리

개인 배포 폴더에 `migration-result.json`, `binding-rollback.json`, `binding-result.json`, `ingestion-task-state.json`, 각 검증 결과가 있다. 비밀값/원문/벡터를 출력하지 않고 상태를 확인한다. 서비스 소스를 고치면 배포된 사본도 갱신하고 예약 작업을 제어해 재시작한다. 실행 중 요청이 없는지 먼저 확인한다.

BGE 복구는 수집을 멈추고 활성 청크 전체의 `q_1024_vec` 존재 여부를 확인한 후, 기록된 이전 데이터셋 모델과 tenant 기본 모델로 되돌리고 재조회·검색 검증하는 순서다. 이전한 원본 청크에는 BGE 벡터가 남아 있지만 **GTE 전환 이후 새로 생성/교체된 청크에는 BGE 벡터가 없을 수 있다**. 이후에는 단순 바인딩 복구만으로 충분하지 않으며 누락 청크의 BGE 재임베딩이 필요하다. Cloudflare 호출은 이 배포에서 하지 않았다.

2026-10-14 시작 구성 정리: Windows Compose의 `full` 프로필은 BGE를 시작하지 않으며 API도 BGE의 상태를 기다리지 않는다. BGE 서비스는 명시적인 `bge-cpu` 프로필로만 선택한다. 이미 중지된 컨테이너가 있으면 `wsl.exe -d Ubuntu --exec docker start docmind-windows-dev-bge-m3-cpu-1`로 시작할 수 있다. 새로 생성해야 할 때는 기존 프로젝트의 실제 env와 전체 배포 Compose 파일을 사용하여 `--profile bge-cpu up -d bge-m3-cpu`로 해당 서비스만 시작한다. 서비스 정상 상태를 확인한 뒤 위의 벡터·바인딩 복구 절차를 수행한다. 서비스 시작만으로 GTE 바인딩이 BGE로 바뀌지는 않는다. 기존 컨테이너·이미지·모델 캐시·볼륨은 보존하며, 이미 중지된 BGE의 현재 CPU/RAM 사용량을 추가로 줄이는 변경은 아니다.

현재 보관된 BGE 필드는 복구용 추가 저장량이다. GTE는 청크당768차원 벡터1개를 사용하며 다중 벡터 모델을 도입한 것은 아니다. 기존 BGE 벡터 삭제는 이 작업에 포함하지 않았다.
