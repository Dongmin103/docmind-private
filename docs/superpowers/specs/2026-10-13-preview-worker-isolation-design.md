# DocMind 미리보기 작업 분리 설계

작성일: 2026-10-13 (Asia/Seoul). 상태: 사용자에게 제시하는 구현 기준안. 이 문서는 실행·배포 완료 기록이 아니다.

## 목적과 범위

문서 검색·청크 대조 화면에서, 색인 서버의 긴 응답 대기 때문에 원문 미리보기가 시작조차 못 하는 문제를 해결한다. 사용자는 계획 작성을 요청했고 구현 모델을 **GPT-6.1 Sol, high (`gpt-6.1-sol`, `high`)**로 지정했다. 이번 산출물은 설계와 구현 계획이며 구현 실행은 후속 단계다.

선택한 방법은 기존 Windows 작업자를 색인 전용 1개와 미리보기 전용 1개로 나누는 것이다. 같은 코드와 기존 Docker 서비스를 재사용한다. 별도 DocMind 서버·OCR·임베딩 모델·영구 원문 캐시를 추가하지 않는다. 중앙 작업 스케줄러 신설이나 색인 API 전체 비동기화는 이번 범위에서 제외한다.

## 근거와 구분해야 할 장애

- 10:58 색인 작업은 복호화 약 0.12초, 서버 전달 응답 대기 약 531.6초였다. 같은 시간대 미리보기는 작업자 미배정 상태로 120초 대기 제한에 걸렸다.
- 현재 `Invoke-LeasedDecryptJob`은 복호화뿐 아니라 서버 응답을 기다리는 동안에도 전역 mutex를 유지한다.
- 별도로 WSL 커널에서 `vmbus_alloc_ring`의 order-7 메모리 할당 실패와 `UtilAcceptVsock` 대기 오류가 확인됐다. 진단 당시 WSL swap 4GiB는 사실상 가득 찼다. 이 장애는 작업 분리만으로 해결되지 않는다.
- 재시작 후 한 시점의 측정: Windows 작업자 약 87MiB, 미리보기 처리기 약 35MiB, DocMind 본체 약 3.76GiB/4GiB, BGE 약 2GiB, Windows 가용 메모리 약 1.65GiB. 이는 순간값이고 부하 시험 결과가 아니다.
- 원문·세션 ID·자격증명·전체 진단 출력은 Git에 넣지 않는다. 로컬 근거는 `.local/preview-wsl-diagnostic-20261013/`에 있다.

## 작업자와 수명주기

1. 실행 인자는 `-Purpose ingest|preview`로 통일한다. 기본값은 `ingest`다. 기존 `-PreviewOnly` 호출부를 함께 전환하고 혼합 실행 분기를 제거한다. 기존 `-Once`, 대상 색인 작업, source/형식 필터 계약은 색인 모드에 보존한다.
2. 작업자 ID, 임시 평문 root, 정리 영수증 root, 로그, 예약 작업 이름을 담당별로 분리한다. 전역 복호화 제어 root는 두 작업자가 공유하며 원문·자격증명을 기록하지 않는다.
3. 미리보기는 기존 서명된 preview claim/artifact/status 경로를 사용한다. 색인은 기존 ingest 경로를 사용한다. 작업자는 자신이 담당하는 경로만 claim·정리·영수증 재전송한다.
4. 기존에 등록·승인된 source만 사용한다. 런처를 복사하며 source 범위를 추가하거나 모든 source 접근을 새로 허용하지 않는다. claim 결과가 구성된 source에 없는 경우 복호화하지 않는다.
5. 작업자별 singleton 잠금으로 같은 역할이 두 번 실행되지 않게 한다. Windows 예약 작업의 중복 실행 금지와 함께 검증한다.
6. 미리보기 정상 idle polling은 1초, 연결 실패 backoff는 5초다. 색인 idle polling은 현행 5초다. 미리보기 요청이 없어도 모델이나 복호화 프로세스를 시작하지 않는다.

## 복호화 실행 제어

- 실제 uEncryptor2 실행은 시스템 전체에서 계속 1개다. 기존 전역 mutex 이름을 유지한다. 실행 중인 색인 복호화를 선점·강제 종료하지 않는다. 엄격한 미리보기 우선순위나 공정성을 mutex만으로 보장한다고 설명하지 않는다.
- 전역 잠금 구간은 프로세스 시작부터 종료 확인 및 출력·원본 무결성 검사까지다. 업로드·변환 응답·정리 ACK 대기는 잠금 밖으로 옮긴다. 잠금 해제는 한 번만 수행한다.
- 미리보기 잠금 대기는 최대 30초이며 작업 lease 잔여 시간에서 10초 안전 여유를 뺀 시간보다 길 수 없다. 1초 이하 간격으로 취소·만료를 재확인한다. 계속 사용 중이면 `PREVIEW_DECRYPT_BUSY`로 종료하고 명확한 재시도 안내를 제공한다. 유효시간을 임의 연장하지 않는다.
- `POST /cloud-sync/host-worker/previews/<id>/validate`를 추가한다. 기존 worker HMAC 인증·서명 응답을 사용하며 body는 `worker_id`, `version_id`, `fencing_token`이다. session의 작업자·fence·lease·DECRYPTING 상태·사용자 권한·원본 버전을 재검증한다. 성공 시 `valid: true`, 현재 `lease_expires_at`을 반환하며 DB 상태를 변경하지 않는다.
- 잠금 획득 뒤에도 위 검증과 원본 hash 검사를 다시 통과한 경우에만 복호화를 시작한다. 실행 중 취소는 원문 결과를 게시하지 않으며 기존 프로세스 timeout·정리 경로로 종료한다. 진행 중 exe의 즉시 취소는 이번 목표가 아니다.
- 종료 확인 실패를 정상 완료로 처리하지 않는다. 공유 제어 root에 차단 상태를 원자적으로 남기고 두 작업자 모두 새 복호화를 거부한다. 자동으로 차단 상태를 지우거나 mutex만 풀어 다음 작업을 실행하지 않는다.
- 부모 작업자 강제 종료/abandoned mutex도 시험한다. 실행 소유 기록(PID, 시작 시각, 실행 파일 식별, 단계)을 공유 root에 두고, 살아 있는 기존 복호화 프로세스가 없다고 확인하기 전 재진입하지 않는다. 시작 도중 소유 기록이 불완전한 경우도 차단한다. 부모 종료 후 남는 자식 프로세스를 관리할 수 없는 구현은 통과로 간주하지 않는다.

## 정리와 실패 처리

- 각 담당만 자신의 임시파일과 영수증을 정리한다. 재시작 시 시간 경과만으로 사용 중인 파일을 삭제하지 않는다. 해당 역할의 singleton, 프로세스 소유 기록, lease와 함께 판단한다.
- 기존 작업자 설정에서 새 root로 전환할 때 남아 있는 예전 영수증은 이전 worker ID·fence를 보존해 재전송한다. 파일·영수증이 남아 있는데 작업자 ID만 바꾸지 않는다.
- 전송 응답 대기는 헤더 수신뿐 아니라 body 읽기까지 제한한다. 오류·취소·통신 단절 경로에서 평문 정리와 상태 ACK 실패를 따로 기록한다. 종료 실패를 `COMPLETE`로 덮어쓰지 않는다.
- 문서 내용·물리 경로·토큰·키를 로그에 남기지 않는다. 작업 ID/fence, 단계별 시간, 허용된 오류 코드와 정리 성공 여부만 기록한다.

## 메모리·화면 계약

- 복호화 동시 실행 1개, 미리보기 변환 동시 실행 1개를 유지한다. 색인 작업자 수도 1개를 유지한다.
- 현행 입력 64MiB, 파생물 16MiB, 총 예약량 96MiB, 세션 수 2개, 공유 tmpfs 128MiB, 처리기 256MiB 제한을 늘리지 않는다. 이 숫자는 전체 프로세스 메모리의 합계 상한이 아니다.
- 기존 본체·처리기를 재사용한다. 브라우저에서 교체·닫기 시 요청과 blob URL을 해제한다. 미리보기 상시 선복호화·캐시·여러 페이지 선생성은 추가하지 않는다.
- 브라우저 준비 상태 polling은 1초로 한다. heartbeat 30초와 기존 만료 정책은 보존한다. 서버 데이터로 확인되는 단계만 표시한다. DECRYPTING 상태만으로 실제 exe가 실행 중이라고 단정하지 않고 '복호화 준비 중'으로 표시한다.
- HWP의 전체 예약량 점유와 열린 세션으로 인한 용량 대기는 기존 한도를 보존한다. 복호화 잠금 대기 및 공간 부족을 일반 네트워크 오류로 표시하지 않는다.
- BGE 필요 여부는 모델 바인딩·실제 요청 경로를 읽기 전용으로 조사한다. 미사용이 확인돼도 이 계획 실행만으로 BGE 중지·삭제, 메모리 제한 변경, 모델 교체를 자동 수행하지 않는다. 별도 근거와 적용안을 제시한다.

## 검증과 적용 기준

기능: 합성 색인 응답을 540초 지연시켜도 작은 PDF 미리보기가 그 응답보다 먼저 완료돼야 한다. 잠금 사용 중·취소·만료·원본 교체·전송 단절·종료 실패·작업자 강제 종료·재시작·두 탭 동시 열기를 시험한다. 단순 mock 호출 횟수뿐 아니라 실제 두 Windows 프로세스의 겹침과 잠금 해제를 검증한다.

응답 목표: 사전 기동된 환경의 1MiB 이하/5쪽 이하 합성 PDF에서, 색인 응답 지연 중 20회 클릭→첫 페이지 표시의 p95가 5초 이내. 로그인·브라우저 초기 실행은 제외하고 요청 시작부터 화면 표시까지 측정한다. 큰 PDF·PPTX·HWP는 별도 측정하며 5초를 공통 SLA로 주장하지 않는다.

제안하는 배포 판정선: 5분 idle 기준선 후 15분 이상 겹침 시험. 새 OOM kill·WSL 할당 오류 0, Windows와 WSL의 가용 메모리는 각각 1GiB 이상, WSL swap은 기준선 대비 증가 128MiB 이하이며 종료 시 512MiB 미만. 각 관련 cgroup의 관측 peak는 한도의 90% 이하. 공유 tmpfs를 단순 합산해 중복 계산하지 않는다. 이미 기준선을 통과하지 못하면 배포를 보류하고 메모리 조정을 별도 과제로 보고한다. 위 수치는 이번 변경을 위한 보수적 제안이며 기존 서비스 보장 수치가 아니다.

배포는 기존 컨테이너 이미지·예약 작업 XML·런처·설정·해시를 보존한 뒤 진행한다. 실제 호출되는 `.local` 배포 사본까지 전환해야 한다. 구버전과 신버전 작업자가 섞여 실행되지 않게 하며 진행 중 작업·임시파일·미확인 종료가 있으면 강제 전환하지 않는다. 원복 시 새 두 작업자를 정지·정리하고 기존 작업자 하나만 복구한다. DB/색인 초기화, 원본 변경, 전체 재색인은 포함하지 않는다.
