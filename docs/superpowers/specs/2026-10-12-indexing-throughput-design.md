# 전체 인덱싱 대기 시간 개선 설계

작성일: 2026-10-12 (Asia/Seoul)
상태: 사용자 설계 검토 대기 — 제품 코드 변경 전
조사 기준: `e369995`, 신규 파일 대기 개선 커밋 `4a9da76` 포함

## 목적과 범위

최초 스캔 시작부터 마지막 대상 문서가 검색 가능해지는 시점까지의 시간을 줄인다. 사용자가 승인한 우선순위에 따라 첫 변경 묶음은 작업 후 고정 휴식, 초기 스캔의 고정 대기, 감시기의 확인 처리량, 스캔 중 처리 개시를 다룬다. 검색 모델·청크 크기·파싱 결과와 호스트 복호화 동시성 1은 유지한다.

임베딩 배치 확대, 제목 요청 통합, 제한적 동시 호출, 단계 간 병렬화, 캐시는 후속 묶음이다. 첫 묶음 전후의 병목을 다시 측정해 적용 순서를 결정한다. 이번 설계는 운영 서비스 재시작·배포·실제 문서 전체 재인덱싱 실행을 포함하지 않는다.

성공 기준은 합성 입력에서 불필요한 고정 대기가 사라지고, 안정성·세대 검증·복구 계약이 유지되는 것이다. 기존 집계는 진행 중 문서 제외와 측정 범위의 한계가 있으므로 전체 처리 시간 보장값으로 사용하지 않는다.

## 현재 코드에서 확인한 사실

- `Start-DocMindUEncryptorHostWorker.ps1`은 작업 처리 여부와 관계없이 루프 끝에서 `PollSeconds`만큼 쉰다.
- `DocMindSyncQueue.cs`는 최초 `create`에만 즉시 확인 자격을 부여한다. 일반 `upsert`는 마지막 이벤트로부터 120초를 기다린다. 첫 관찰 ACK 뒤에는 10초 재확인이 필요하다.
- `Invoke-DocMindSourceReconciliation.ps1`은 파일을 열거하면서 모두 `upsert`로 큐에 넣는다. 따라서 초기 스캔은 새 파일 이벤트 최적화를 사용하지 않는다.
- 감시기는 이미 스캔을 별도 프로세스로 실행한다. 전체 스캔 완료를 반드시 기다리는 새 구조를 해체할 필요는 없다.
- 감시기는 한 source에서 주기마다 dirty 전달 또는 due 파일 하나를 처리한다. 큐는 `due_at,path_key`로 정렬하므로 첫 확인 대상이 많이 남으면 재확인이 지연된다.
- 서명된 outbox는 source별 하나이며, ACK 전 재전송 payload와 sequence를 고정한다. 세대가 바뀐 파일은 오래된 ACK로 지워지지 않는다.
- 스캔의 파일 열거 자체도 해시를 읽는다. 이번 변경에서는 해당 일관성 검사를 제거하거나 스캔의 해시를 두 번의 시간 간격 관찰로 간주하지 않는다.

## 접근 선택

1. 워커 휴식만 제거: 변경 범위는 작지만 초기 등록 병목이 남는다.
2. 기존 큐·서명 프로토콜 안에서 대기와 스케줄링 개선: 첫 변경 묶음으로 선택한다.
3. 복호화·파싱·임베딩 워커를 병렬로 증설: 자원 및 공급자 제한 검증이 필요하므로 후속으로 둔다.

## 1. 워커 연속 처리

정상 처리와 상태 ACK·평문 정리가 끝나면 다음 claim을 즉시 수행한다. 작업이 없거나 통신·인증·claim 오류가 난 경우에는 기존 polling 대기를 유지해 빈 루프를 방지한다.

문서 처리 실패와 워커 기반시설 실패를 구분한다. 실패 상태 ACK와 정리가 확인된 문서 오류만 다음 작업으로 즉시 넘어갈 수 있다. 상태 전달이나 정리가 불확실하면 오류 대기를 유지한다. 미리보기/인덱싱 선택 순서와 연속 미리보기 제한, `Once`, 특정 작업 claim 옵션은 유지한다.

## 2. 스캔 관찰 등록 분리

스캔은 변경 이벤트가 아니라 현재 존재하는 파일의 관찰이다. 큐에 전용 스캔 등록 동작을 추가해, 해당 경로에 pending 항목이 없으면 즉시 첫 확인 대상으로 등록한다. 서버에 전달하는 변경 종류는 기존 `upsert`를 유지한다.

이미 pending 항목이 있으면 스캔은 그 항목의 세대·수정 대기·이동 정보·삭제 상태·첫 fingerprint·outbox를 초기화하지 않는다. 일반 수정 이벤트는 계속 120초 정책을 따른다. 스캔만 반복해서 재시도 시각을 뒤로 밀거나 두 번째 확인을 초기화하는 일이 없어야 한다.

스캔으로 등록된 뒤 파일 변경을 관찰하면 이전 안정성 증거는 폐기한다. 두 번의 동일 fingerprint 관찰과 해시 전후 크기·수정 시각·파일 identity 검사를 계속 요구한다. epoch 변경 후에도 스캔 후보에 임의의 120초 대기를 다시 붙이지 않는다. 기존 큐 파일의 스키마 변경은 기존 초기 등록 플래그로 충분한지 먼저 확인하고 최소화한다.

## 3. 감시기의 처리량과 재확인 우선순위

source별 한 번의 방문에서 여러 due 항목을 처리하도록 한다. 초기 기본 상한은 32개, 경과 시간 예산은 1초로 두고, 파일 하나의 동기 해시 작업은 중간에 취소하지 않는다. 따라서 시간 예산은 다음 항목을 시작할지 판단하는 기준이며, 느린 파일 하나의 수행 시간을 보장하는 제한은 아니다.

이미 재확인 시각이 된 항목을 첫 확인보다 우선한다. 상한은 source 간 공정성과 세션 갱신을 위한 것이며 전체 큐를 무제한 비우지 않는다. 성공적으로 작업을 진행했고 즉시 처리 가능한 항목이 남았다면 전체 source 순회 후 고정 polling 휴식 없이 다음 순회를 시작한다. 미래에만 due가 되거나 모든 source가 재전송 대기/보류 상태면 쉰다.

dirty ACK 뒤 같은 방문에서 due 작업을 진행할 수 있도록 하되, 연속 dirty 이벤트가 재확인을 영구적으로 밀어내지 않게 한다. 수정 사실 전달도 무기한 지연시키지 않는다.

첫 구현은 기존 항목별 서명 outbox 전송을 유지하고 source 방문당 여러 항목을 처리한다. 여러 파일의 해시를 거대한 HTTP 요청 하나로 묶는 것은 이번 성능 개선의 선행 조건이 아니다. 이 방식은 해시 중 한 파일의 세대가 바뀌어 전체 묶음이 계속 취소되는 문제도 피한다.

미확인 outbox가 남거나 세션이 만료/교체되면 해당 source 처리를 즉시 멈춘다. 파일 하나의 읽기 오류는 해당 항목만 지연하고 다른 준비된 항목은 처리한다. source 자체에 대한 장애는 재시도 정책을 유지한다.

## 4. 스캔 중 처리와 지원 형식

기존 스트리밍 열거와 별도 스캔 프로세스를 유지한다. 준비된 문서는 스캔 완료 이벤트보다 먼저 두 번의 안정성 확인을 통과해 처리될 수 있다. 삭제 후보 확정은 여전히 전체 스캔 성공 후에만 한다.

지원하지 않는 파일을 큐에 넣지 않는 최적화는 전체 스캔 존재 목록과 분리한다. 지원 형식은 현재 서버 계약인 pdf/doc/docx/xls/xlsx/pptx/hwp/hwpx와 일치시킨다. 전체 존재 목록에서 파일을 누락해 삭제로 오인하게 만들면 안 된다. 삭제·이동 이벤트와 이미 등록된 문서의 상태 갱신을 확장자만으로 무시하지 않는다. 기존 등록 문서까지 안전하게 판별할 근거가 없는 경로에는 보수적으로 기존 처리를 유지한다.

## 검증

제품 코드를 바꾸기 전에 회귀 테스트로 현재 지연과 변경 조건을 재현한다. 사용자 원본·운영 큐·공급자 API는 시험에 사용하지 않는다.

1. 워커: 준비된 연속 작업 사이 고정 휴식 없음, 빈 큐·통신 오류 시 대기 유지, 문서 실패 후 ACK/정리 확인, 미리보기 공정성과 `Once` 유지.
2. 큐: 스캔 항목 즉시 due, 기존 수정의 120초 유지, 스캔과 수정/삭제/이동 경합 시 세대 보존, 10초 재확인, 재시작/epoch 변경, 오래된 ACK 차단.
3. 감시기: 여러 파일이 한 방문에서 진행, 재확인 우선, 한 파일 오류의 격리, source 간 순회, 서명/sequence/미확인 outbox의 재시도 유지.
4. 합성 통합: 느리게 끝나는 스캔에서 앞선 파일의 두 번째 관찰이 스캔 완료보다 먼저 전달됨을 검증한다. 스캔 실패가 대량 삭제 권한을 만들지 않는지도 확인한다.
5. 성능 비교: 같은 합성 파일 집합으로 변경 전후를 비교한다. 파일 수·바이트 수·source 수를 고정하고 첫 관찰/두 번째 관찰 시각과 전체 큐 해소 시각을 기록한다. 120초 대기 경계는 가상 시각을 쓰는 큐 테스트로 검증하고 시험을 위해 실제로 2분씩 기다리지 않는다.
6. 실제 전체 인덱싱의 검색 가능 시각은 이후 사용자 문서 벤치마크에서 검증한다. 합성 큐 시험의 단축률을 임베딩까지 포함한 전체 성능으로 보고하지 않는다.

## 결과와 후속 단계

변경 파일과 회귀 검증 결과는 기능별 Git 커밋으로 기록한다. 배포 파일과 현재 소스의 차이를 확인한 뒤 적용 범위를 별도로 제시한다. 배포 전까지 실행 중인 서비스 성능이 개선됐다고 보고하지 않는다.

첫 묶음의 측정 후 임베딩 호출 수·입력 토큰·응답 시간·재시도 시간을 분리한다. 그 결과를 바탕으로 배치 확대와 제목 요청 통합을 다음 구현 묶음으로 설계한다.
