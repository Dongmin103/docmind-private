# 클라우드 문서 처리 전용 구성 정리

## 변경 범위

- Python 배포의 외부 커넥터 API·서비스·구현과 데이터 소스 관리 화면을 제거한다. 데이터셋 생성·수정 요청의 외부 커넥터 필드도 거절한다.
- 별도 task executor와 datasync 실행 코드를 삭제하고 기본 시작 경로에서 제거한다. 현재 DocMind 인덱싱이 직접 호출하는 `TaskHandler`와 공통 파싱·청킹·임베딩·색인 처리는 유지한다.
- Windows 원본 감시, 인덱싱, 검색, 미리보기, 모델 설정은 유지한다. DB 테이블과 기존 원본을 삭제하는 마이그레이션은 없다. 대체 Go 서버 구현은 이번 Python 배포 정리 범위 밖이다.
- 인덱싱 복호화 잠금의 고정 5초 대기를 작업 임대 만료 시각까지의 안전 예산으로 바꾼다. 미리보기의 30초 대기 상한과 호스트 전체 단일 복호화 프로세스 제한은 유지한다.
- 대기 중, 잠금 획득 후, 실제 복호화 직전에 서명된 서버 API로 현재 작업 소유자·fence·상태·버전·원본 관측값·만료를 검증한다. 임대 연장 없이 취소되거나 바뀐 작업은 실행하지 않는다.

## 검증

- 외부 커넥터 제거 백엔드 회귀 49개, 프런트 7개 스위트 37개 통과.
- 인덱싱·파서·인증·스토리지 관련 158개 및 임베딩·청크 계약 48개 통과.
- 새 권한 검증을 포함한 인덱싱 서비스·HTTP 경로 124개 통과. 위 집계와 일부 중복된다.
- 실제 SQLite 모델과 보호 로직을 실행한 문서 보호 회귀 70개 통과. 외부 검색·저장소 연결만 테스트에서 격리했다.
- 실제 별도 프로세스가 7초간 잠금을 잡는 Windows 회귀 시험에서 5초를 넘겨 대기한 뒤 진행한다. 임대 만료, 대기 중 취소, 잠금 획득 직후 취소 시 복호화 실행이 차단된다.
- Windows 단일 복호화 프로세스·시간 초과·정리·슬롯 풀 시험과 Linux 기본 시작 경로 시험 통과.
- 잠금 파일 기반 `npm ci` 후 프로덕션 빌드 통과. 프런트 전체 타입 검사에는 기존 오류가 남는다(기준 206개, 변경 후 201개; 새 파일/오류 코드별 증가 없음). 변경 부분 lint 통과.
- 제거된 제품 경로 검사 통과. 재검토에서 복호화 전 서버 권한 검증 지적이 해소됐다.

## 배포·실측 기준

문서 동시성 4, 파서 2, 파서 CPU 한도 4, GPU 추론 1, 짧은 배치 16과 채움 기준 85%를 유지한다. OCR은 요청하지 않는다.

암호화 원본 244개와 등록 식별자를 보존하고 파생 청크·벡터를 초기화한 뒤 1회씩 처리한다. 정상 문서 223개/12,460청크와 벡터, OCR 필요 PDF 18개, 기존 입력 오류 3개를 확인한다. 작업 시간, 시작·최종 정리 ACK 포함 시간, GPU 사용률·VRAM, 메모리와 OOM/재시작을 각각 기록한다. 이전 대기 오류 포함 실행 시간을 완전 성공 기준으로 사용하지 않는다.

배포 후 전체 1회 실측과 정합성 검증을 완료했다. 원본 식별자·경로·내용을 제외한 수치는 [측정 기록](measurements/full-reindex-noocr-cleanup-2026-10-14.json)에 보관한다.

고정 대기 제한 오류, 작업 권한 만료 오류, 새 호스트 처리 오류는 없었다. API 컨테이너의 메모리 한도 도달·OOM 이벤트는 0이고 API/파서 재시작도 없었다. SQL의 활성 청크 집합, 검색 색인 12,460건과 GTE 벡터가 일치한다. 원본 244개의 해시·크기·수정 시각이 보존됐고 호스트·파서 임시 파일과 미완료 정리는 0이었다. OCR 실행은 0건이다. 잘못된 HWP 1건은 첫 시도에서 형식 오류로 끝난 후 스케줄러가 `RETRY_WAIT`로 이동했으며, 이번 측정에서 재시도하지 않았다.

이 수치는 이미 실행 중이고 앞선 부분 처리로 예열된 API·파서·모델에서 측정했다. 원본 발견, 초기화 준비와 서비스 부팅 시간은 제외한다. 측정 중 원본 감시와 미리보기 워커는 일시 중지했고, GPU·CPU·RAM 수치는 전체 장치/호스트 기준이다. API cgroup 누적 최고값 3.52GiB는 컨테이너 시작 이후 값이며 실측 구간 샘플 최고값과 구분한다.

GPU 평균 80% 목표에는 도달하지 않았다. RAM 여유가 적으므로 이번 1회 통과를 장시간 안정성이나 검색 혼합 부하 검증으로 해석하지 않는다. 이전 전체 실행에는 OOM 또는 대기 오류가 있어 동일 성공 조건의 속도 개선율을 계산하지 않는다.

## 실측에서 발견한 시각 정밀도 문제

첫 배포 후 시도는 23개 작업 중 17개가 `DOCMIND_INGESTION_STALE_LEASE`로 거절돼 중단했다. 정상 완료 5개와 OCR 필요 1개, 미시도 221개였으며 진행 작업과 임시 파일 정리를 마친 뒤 수정했다. 이 실행을 성공 시간이나 성능 비교 근거로 사용하지 않는다.

운영 MySQL의 임대 만료 열은 `DATETIME(0)`이고 소수 초를 반올림하지만, 워커 응답은 소수 초를 버렸다. 따라서 두 시각이 1초 달라질 수 있었다. DB 저장 전에 초 단위로 정규화해 저장값과 응답값을 같게 했다. 임대는 최대 1초 미만 짧아지며 연장되지 않는다. 워커의 엄격한 일치 검사는 유지했다.

반올림 경계 전후 5개 값과 3개 임대 길이의 15개 회귀 사례는 수정 전 실패, 수정 후 통과했다. 전체 인덱싱 서비스·HTTP 경로 검증은 139개 통과했다.

후속 시도는 복호화 시작 전 호스트 오류 3건 때문에 중단했다(139개 시도, 정상 132개, OCR 필요 3개, 잘못된 HWP 1개). 이 실행도 성공 시간에서 제외했다. 당시 API 응답 지연과 미리보기에서 가져온 1초 검증 요청 제한이 충돌할 가능성을 확인했다. 실제 1.5초 지연 HTTP 응답에서 취소 예외를 재현했으며, 취소를 안전한 `API_REQUEST_TIMEOUT`으로 구분하도록 했다.

인덱싱 검증 요청은 `min(10초, 작업 임대 안전 마감까지 남은 정수 초)`로 제한한다. 응답을 확인하지 못하면 여전히 복호화를 시작하지 않는다. 미리보기의 1초 요청 제한, 단일 복호화 실행, 서버 권한 검사와 실행 전 만료 확인은 유지한다. 실제 HTTP 지연 시험과 13초 임대의 잔여 요청 예산 시험을 포함한 Windows 회귀가 통과했다.
