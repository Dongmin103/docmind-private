# 클라우드 전용 배포의 보조 프로세스 메모리 시험

2026-10-14. 사용자가 보조 서비스 정리와 현재 최적 설정의 전체 1회 재측정을 승인했다.

## 적용 범위

현재 로컬 배포의 API 실행 인자에 `--disable-taskexecutor --disable-datasync`를 추가했다. `--enable-adminserver --init-model-provider-tables`는 유지했다. 실행 이미지와 메모리 한도(4GiB), 문서 동시성 4, 파서 2/CPU 한도 4, GPU 추론 1/짧은 배치 16/최소 채움 85%는 변경하지 않았다.

코드에서 클라우드 인덱싱은 `ProductionTemporaryParserInputRunner`가 API 내부에서 `TaskHandler.handle_task()`를 직접 실행한다. 적용 전 실제 DB에 외부 커넥터/연결/캔버스가 없고, 모든 244개 문서가 `docmind_cloud`이며, 일반 작업 큐 두 개의 pending/lag가 모두 0임을 확인했다. 외부 커넥터를 담당하는 `sync_data_source.py`와 일반 Redis 큐 실행기 `task_executor.py`만 비활성화했다. 관리자 API는 nginx의 `/api/v1/admin` 경로에서 사용하므로 유지했다.

이 설정은 현재 클라우드 전용 배포에 한정한다. 외부 커넥터, 일반 업로드 큐, 캔버스 등 별도 실행기를 사용하는 기능을 도입할 때는 의존성과 전체 메모리 예산을 다시 검토해야 한다. Windows 원본 감시기는 이 두 프로세스와 별개이며 시험 후 정상 실행으로 복구했다.

## 실측

- 변경 전 유휴 Docker 메모리: 3.922GiB / 4GiB.
- 변경 후 처리 전 유휴 Docker 메모리: 1.991GiB / 4GiB. 새 프로세스로 재기동한 효과도 포함하므로 차이 전체를 서비스 제거 효과로 단정하지 않는다.
- 전체 첫 시도 중 cgroup 메모리 최고치: 3.278GiB. 한도 도달 이벤트, OOM, OOM kill 모두 0. API와 관리자 프로세스 PID도 유지됐다.
- 첫 문서 시작부터 마지막 정리/ACK까지: 287.53초. 워커 시작부터는 292.55초, 5초 주기 관찰 종료는 294.92초.
- GPU 평균 53.57%, 문서 작업 구간 평균 55.01%, 최고 100%, VRAM 최고 8,005MiB.
- 첫 시도는 220개 색인/12,335개 청크. OCR 필요 18개, 잘못된 파일 3개 외에 복호화 게이트 대기 초과 3개가 발생했다. 따라서 정상 전체 완료 시간이나 확정 속도 향상률로 사용하지 않는다.

## 배포 및 복구 기록

실제 적용값은 무시되는 `.local/parser-424-deploy-20261013/release-compose.private.json`에 저장했다. 원래 manifest는 `.local/full-reindex-noocr-lean-20261014/rollback-compose.private.json`에 보존했다. 두 파일에는 비밀값이 포함될 수 있으므로 Git에 추가하거나 내용을 공개하지 않는다.

롤백할 때는 수집/미리보기/원본 감시 작업을 일시 중지하고 모든 진행 작업과 정리/ACK가 끝난 것을 확인한다. 보존한 원래 manifest로 현재 release manifest를 복구한 뒤 `ragflow-cpu`만 `up -d --no-deps --no-build`로 재생성하고 API/관리자/GPU/파서 상태를 확인하여 워커와 감시기를 재개한다. DB/색인/암호화 원본은 롤백 대상으로 삭제하지 않는다. 이전 4GiB 메모리 문제가 돌아올 수 있으므로 단순히 두 보조 서비스를 다시 켜는 것을 메모리 문제 해결로 취급하지 않는다.

남은 문제는 복호화 게이트의 5초 대기 제한이다. 이번 시험에서는 설정을 유지했고, 이를 변경해 다른 조건의 결과를 섞지 않았다.
