# GPU 추론 동시성 2: 단회 비교와 내부 시간

사용자 요청대로 **GPU 추론 2만 실측 1회** 수행했다. 추론 1은 이전 324 결과를 재사용했다. 새 결과는 **26.99초**, 이전은 **22.93초**로 이번 전체 처리는 **17.7% 느렸다**. 그러나 파싱 시간이 크게 증가했고 임베딩 단계 합계는 소폭 감소했으므로, GPU 추론 2 자체가 17.7% 느려졌다고 해석하면 안 된다. 이 비교로는 상시 추론 2 채택의 이점이 입증되지 않았다.

## 비교

| 항목 | 추론 1: 이전 실측 | 추론 2: 새 실측 |
| --- | ---: | ---: |
| 전체 처리 시간 | 22.93초 | 26.99초 |
| GPU 평균 / 최대 | 56.9% / 100% | 49.9% / 100% |
| VRAM 최대 | 4,793 MiB (4.68 GiB) | 6,291 MiB (6.14 GiB) |
| 성공 문서 / 검색 가능 벡터 | 14 / 885 | 14 / 885 |
| API 임베딩 단계 합계 | 25.18초 | 23.76초 |
| 파싱 HTTP 단계 합계 | 11.54초 | 23.96초 |
| 파서 프로세스 응답 구간 합계 | 9.895초 | 20.284초 |
| 파서 CPU 사용량 | 13.90 CPU초 | 24.72 CPU초 |
| 파서 CPU 제한 대기 | 0초 | 0초 |

단계 합계는 여러 문서가 겹쳐 실행된 시간을 누적한 값으로, 전체 처리 시간에 더하거나 그 비율로 병목 비중을 계산하지 않는다. 임베딩 합계는 약 5.6% 감소했지만 전체 시간은 증가했다. 큰 PDF의 파싱 HTTP 구간은 4.12→7.56초, 임베딩 시작점은 약 12.86→18.18초로 늦어졌다. 해당 PDF의 임베딩 구간 자체는 9.62→8.86초였다. HWP의 임베딩 구간도 9.84→8.57초였다. API UTC와 호스트 UTC의 경계에는 작은 시각 오차가 있어, 전체 시간은 기존과 동일하게 호스트 첫 시작~마지막 정리/ACK 완료를 사용했다.

관측상 문서 준비 지연이 전체 종료 시점을 늦췄다. 추론 동시성 증가에 따른 CPU 실행/메모리 경쟁, 문서 처리 순서 및 환경 변동은 가능한 원인이다. 파서 CPU 사용량 자체도 증가해 단순 CPU 할당 제한으로 설명되지 않는다. 프로세스별 CPU 프로파일이나 같은 시점의 추론 1 재측정은 수행하지 않았으므로 원인은 확정하지 않았다. GPU 사용률이 낮아진 것도 입력 공급 지연과 함께 해석해야 한다.

## 요청 대기·토큰화·GPU 구간

새 실측 구간에서 서비스 요청 52개가 모두 성공했고, 내부 배치 137개를 기록했다. 모델 한 벌, 추론 슬롯 2개, 서로 다른 CUDA 스트림 2개를 확인했다. 호스트 요청 실행 구간 중첩은 11.15초, 최대 동시 요청은 2였다.

| 계측 항목 | 전체 요청/배치 누계 | 의미 |
| --- | ---: | --- |
| 서비스 추론 슬롯 대기 | 0.667초 | GPU 서비스에 도착한 뒤 슬롯을 기다린 시간 |
| 토크나이저 잠금 대기 | 0.034초 | 공유 토크나이저 보호용 잠금 대기 |
| 토큰화 실행 | 0.261초 | 길이 계산과 배치 tensor 생성 호출 포함 |
| CPU→GPU 전송 호출 | 0.026초 | 호스트에서 관측한 입력 전송 구간 |
| 모델·정규화 CUDA 이벤트 구간 | **21.978초** | 배치별 GPU 스트림 경과 시간 누계 |
| 모델 호출의 호스트 경과 시간 | 11.366초 | Python/PyTorch의 연산 제출 및 호출 대기 |
| GPU→CPU 결과 복사와 완료 대기 | 12.550초 | GPU 작업 완료 대기가 포함된 `.cpu()` 구간 |
| 결과 검사·리스트 변환 | 0.028초 | 차원/유한성 검사와 Python 출력 변환 |

**요청 대기와 토큰화는 작고, 모델 실행 경로가 대부분이다.** 다만 CUDA 이벤트는 스트림의 경과 시간을 재므로 다른 스트림과의 자원 경쟁, 연산 제출 사이 공백 등이 포함될 수 있다. 순수 커널 활성 시간이나 GPU 연산장치 점유율을 직접 측정한 것은 아니다. 모델 호출 호스트 시간, CUDA 이벤트 시간, 결과 복사/완료 대기는 서로 겹친다. 이 세 값을 더하면 안 된다. 여러 스트림의 누계도 전체 벽시계 시간과 다르다.

서비스 내부 요청 집계는 제목 등의 요청도 포함할 수 있어 API의 문서 `embedding` 단계 집계와 범위가 다르다. 공통 기준 시각의 GPU 커널 추적을 수집하지 않았으므로 호스트 요청 중첩을 실제 커널 동시 실행의 증명으로 사용하지 않는다. 더 세밀한 판단에는 CPU 연산 제출 비용과 GPU 실행을 함께 보는 프로파일이 필요하다.

## 고정 조건과 시험 구현

문서 슬롯 3 / 파서 프로세스 2 / 파서 CPU 한도 4, GTE multilingual base 768차원 FP32/eager, 임베딩 요청 동시성 2, 요청 배치 32, 내부 배치 8/2/1, 복호화 1을 유지했다. 이전과 SHA-256이 같은 14문서 manifest를 사용했다. OCR은 껐다. 준비용 합성 동시 요청과 별도 문서 워밍업 후 **추론 2 실측 1회**만 수행했으며 추론 1은 재실행하지 않았다.

`tools/local_embedding/compare_concurrency.py`는 비교용 서버다. 기존 `service.py`의 모델·길이 정렬·배치 분할·OOM 재시도·출력 계약을 재사용하고, 모델 한 벌을 두 스트림에 공유했다. 공유 토크나이저 호출은 짧은 잠금으로 보호하고 스트림 동기화가 끝나야 슬롯을 반환한다. 상시 서비스 코드와 비공개 설정 파일은 수정하지 않았다. 계측은 입력 내용·벡터·인증값을 기록하지 않는다.

기존 모델을 함께 올려 VRAM이 이중 점유되지 않도록 개발 ingest/watcher를 drain한 뒤 원래 GPU 서비스를 잠시 중지했다. Windows 예약 작업 중지만으로 자식 GPU 프로세스가 즉시 사라지지 않아 실측 전 전환이 지연됐다. 실행 파일과 PID를 확인해 종료·포트 해제·VRAM 반환을 확인한 후 후보를 실행했다. 격리 API의 Redis 인증 설정도 실측 전에 정정했다. 이 준비 실패들은 실측 실행이 아니며 시간 비교에 넣지 않았다.

추론 1은 이전 시각의 결과이고 후보에만 추가 계측이 있어, 환경 변동·캐시·할당기 상태·계측 오버헤드가 대칭적이지 않다. 따라서 속도 차이를 추론 동시성 하나의 인과 효과로 주장하지 않는다. 사용자 요청을 따라 추가 반복이나 추론 1 재측정은 하지 않았다.

## 정합성·부하·복구

- 문서 14개와 벡터 885개 모두 성공하고 문서별 청크 수가 기준과 일치했다.
- 기존 라이브 GTE 벡터를 문서와 본문 SHA-256으로 연결해 885개를 읽기 전용 비교했다. 최소 코사인 유사도 0.9999999999991, 최대 성분 차이 약 1.92×10⁻⁷로 수치 오차 범위에서 일치했다. 이 검증에 추가 GPU 추론은 없었다.
- 내부 OOM 이벤트 0, 컨테이너 OOM 0, 호스트/API/파서 임시 작업 파일 잔여 0이었다. WSL 가용 메모리 표본 최소는 2,431.7 MiB, swap 입출력은 39/58페이지였다. 전체 호스트 CPU 경쟁을 배제하는 근거는 아니다.
- 원본 14개의 해시·크기·수정 시각 유지, 시험 컨테이너/DB 제거, 후보 포트 해제, 원래 GPU/API HTTP 200 응답과 GTE/ingest/watcher 예약 작업 Running 복구를 최종 확인했다. 확인값은 연결 JSON에 기록했다.
- 기존 서비스와 비교 어댑터의 집중 테스트 12개가 통과했다. 읽기 전용 별도 리뷰에서 중요한 차단 결함은 없었다.

리뷰의 경미한 보완 사항은 계측 파일 쓰기 실패 시 세마포어 반환 보강, CUDA 동기화 실패 후 차단 동작의 추가 테스트다. 이번 정상 계측 실행에서는 발생하지 않았으며 후보를 상시 배포하지 않으므로 후속 보완으로 남겼다. 모델 내부 가변 상태에 대한 정적 보장은 하지 않았지만 실측 벡터 대조로 이번 입력의 출력 정합성을 확인했다. CUDA 이벤트/호스트 구간 해석과 비대칭 계측 오버헤드는 위 한계에 반영했다.

결론은 **현재 추론 1을 유지**하는 것이다. 이번 실측에서는 추론 2의 전체 처리 이점이 입증되지 않았고 VRAM만 1,498 MiB 증가했다. 다만 임베딩 단계만은 약간 짧아져 추론 2가 원천적으로 느리다는 결론도 아니다. [기계 판독 측정값](measurements/gpu-inference-2-2026-10-13.json)과 이전 [324 결과](CPU-PARSER-324-RESULTS-2026-10-13.md)를 함께 본다.
