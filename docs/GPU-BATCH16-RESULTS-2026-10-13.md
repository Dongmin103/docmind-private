# GPU 내부 배치 8→16: 실측 1회 결과

사용자가 문서 순서 변경보다 배치 크기 조정을 먼저 시험하도록 요청했다. GPU 추론은 1로 두고, 1,024토큰 이하 입력의 GPU 내부 배치만 8→16으로 변경했다. 결과는 **GPU 평균 56.9→61.4%, 전체 시간 22.93→33.72초**였다. 사용률은 올랐지만 전체 처리는 47.1% 느려져 후보를 채택하지 않았다. 원래 서비스의 배치 8/추론 1을 복구했다.

## 비교 조건과 결과

| 항목 | 이전 배치 8 / 추론 1 | 후보 배치 16 / 추론 1 |
| --- | ---: | ---: |
| 전체 시간 | 22.93초 | 33.72초 |
| GPU 평균 / 최대 | 56.9% / 100% | 61.4% / 100% |
| VRAM 최대 | 4,793 MiB | 5,869 MiB |
| API 임베딩 단계 합계 | 25.18초 | 40.08초 |
| 파싱 HTTP 단계 합계 | 11.54초 | 25.08초 |
| 문서 / 벡터 | 14 / 885 | 14 / 885 |

이전 기준선은 기존 324 실측을 재사용했고 새 기준선 측정은 하지 않았다. 준비 확인용 합성 요청, 문서 워밍업, 후보 실측 **1회**를 수행했다. 워밍업과 프로세스 기동/관측 지연은 성능 수치에서 제외했다. 전체 시간은 첫 호스트 문서 시작부터 마지막 정리·ACK 완료까지이고 GPU 표본도 이 구간으로 제한했다.

문서 슬롯 3 / 파서 프로세스 2 / CPU 한도 4 / GPU 추론 1 / 임베딩 요청 동시성 2 / 요청 배치 32 / 복호화 1, 동일 모델 FP32/eager와 청킹을 유지했다. 긴 입력 배치는 1,025~2,048토큰에서 2, 그 이상에서 1로 유지했다. 같은 14문서 manifest SHA-256은 `d9e75e20b8c19560deadc125fd42299dd5b6bfc8997b89aadf6549f16388846f`다.

## 사용률은 올랐는데 왜 느려졌나

배치 내부의 입력 tensor는 가장 긴 입력 길이에 맞춰 패딩한다. 더 많은 입력을 함께 묶으면 짧은 입력의 패딩이 늘 수 있다. 이전에 수집한 **GPU 추론 2 / 내부 배치 8** 계측과 배치 모양만 비교하면, 두 실행 모두 입력은 913개지만 패딩 포함 토큰 수는 **190,434→261,849, 37.5% 증가**했다. 이 913개는 최종 벡터 885개 외 제목 등의 서비스 입력을 포함한다.

배치 8 계측의 내부 배치 호출은 137개, 후보는 83개로 줄었다. 후보에서 실제 16개 배치는 47번 실행됐고 OOM은 없었다. 호출 횟수 감소의 이점과 패딩 계산 증가의 비용이 함께 발생했다. 배치 크기×최대길이²의 합으로 계산한 attention 크기 지표도 57.3% 늘었지만, 이는 tensor 모양에서 얻은 지표이며 실제 FLOPs나 전체 지연 원인을 직접 측정한 값은 아니다.

후보의 파싱 HTTP 구간도 이전보다 늘었다. 기준선은 다른 시각에 측정됐고 후보에만 상세 계측이 추가돼 있어 **전체 47.1% 증가를 배치 하나의 인과 효과로 확정하지 않는다.** 사용률 상승 역시 유효한 처리량 증가를 보장하지 않는다. 이번 단회 결과에서는 GPU 평균 80%에 도달하지 못했고 속도 개선도 확인하지 못했다.

## 내부 시간 분리

후보 서비스 요청 52개 모두 성공, 최대 동시 실행 1개, CUDA 스트림 1개, 내부 배치 83개를 확인했다.

| 항목 | 후보 누계 |
| --- | ---: |
| 서비스 추론 슬롯 대기 | 20.140초 |
| 토크나이저 잠금 대기 | 0.000135초 |
| 토큰화 실행 | 0.247초 |
| 모델·정규화 CUDA 이벤트 구간 | 20.550초 |
| 모델 호출 호스트 경과 시간 | 0.622초 |
| 결과 CPU 복사와 GPU 완료 대기 | 19.989초 |
| 요청 실행 구간 | 21.018초 |

동시에 들어오는 두 임베딩 요청이 추론 슬롯 하나를 공유하므로 한 요청의 GPU 실행과 다른 요청의 슬롯 대기는 겹친다. CUDA 이벤트와 CPU 결과 복사/대기도 겹쳐 **위 수치를 더하면 안 된다.** CUDA 이벤트는 모델·정규화 스트림 경과 시간이며 순수 커널 활성 시간만 분리한 값은 아니다. 토큰화 시간은 작고, 모델 실행과 그로 인한 요청 대기가 주요 구간이었다.

## 구현·검증·복구

비교용 `compare_concurrency.py`에 `--short-batch 16 --inference-slots 1`을 추가했다. 기본 서비스인 `service.py`와 배포된 파일/설정은 변경하지 않았다. 후보도 단일 추론에서는 기본 CUDA 스트림을 사용하고, 기존 정렬·출력 순서 복원·8192토큰 상한·OOM 분할 처리를 유지한다. 일반 배포 기능으로 채택한 변경이 아니다.

추가 테스트의 실패를 먼저 확인한 뒤 구현했고 집중 테스트 14개가 통과했다. 별도 읽기 전용 리뷰에서 중요한 결함은 없었다. 경미한 테스트 보완 두 건(단일 추론 CLI/기본 스트림 연결의 직접 검사, 정확히1024토큰인16개 입력 경계 시험)은 보류했다. 기존 비교 어댑터의 계측 파일 오류 시 permit 보강도 이전 보고서의 보류 사항으로 남아 있다.

14문서와 885벡터의 성공·문서별 청크 수·정리 완료를 확인했다. 기존 라이브 GTE 벡터를 문서/본문 해시로 연결해 885개를 비교했고 최소 코사인 유사도 0.999999 이상으로 일치했다. 검증 과정에서 기준선 GPU 추론을 추가 수행하지 않았다.

원본 14개 해시·크기·수정 시각은 그대로였다. 후보 OOM 0, 컨테이너 OOM 0, host/API/parser 임시 작업 파일 잔여 0이다. 시험 컨테이너와 DB를 제거하고 후보 포트를 해제했다. 원래 GTE와 API HTTP200 및 GTE/ingest/watcher 예약 작업 Running을 확인했다. 비공개 로그는 `.local/gpu-batch16-20261013`에, 공유 가능한 수치는 [측정 JSON](measurements/gpu-batch16-2026-10-13.json)에 저장했다.

이번에는 배치 8을 유지한다. 후속 후보는 단순한 개수 확대보다 비슷한 토큰 길이끼리 묶거나 토큰/attention 크기 예산으로 배치를 제한하는 방식이다. 이 후속 변경과 추가 실측은 이번 작업에 포함하지 않았다.
