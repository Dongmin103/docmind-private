# 길이별 GPU 배치: 실측 1회 결과

GPU 배치의 패딩 낭비는 줄었지만 전체 파이프라인에는 GPU 밖의 긴 지연이 남았다. 기존 배치 16 대비 전체 시간은 33.72→28.85초로 14.5% 줄었고, 모델·정규화 CUDA 이벤트 시간 합계는 20.55→10.54초로 줄었다. 이전 배치 8 기준선 22.93초보다는 25.8% 느리므로 운영 설정에는 채택하지 않았다. 원래 GPU 서비스를 복구했다.

## 조건과 결과

기존 서비스도 요청 안에서 입력을 길이순으로 정렬한다. 이번 후보는 정렬 후 짧은 입력을 최대 16개 묶되, 실제 토큰 합계 / 패딩 포함 토큰 수가 85% 이상인 동안만 배치를 확장한다. 1,025~2,048토큰은 배치 2, 그 이상은 1을 유지했다. GPU 추론 1, 모델 1개, 기본 CUDA 스트림 1, 요청 배치 32, 임베딩 요청 동시성 2, 문서 슬롯 3, 파서 프로세스 2, 파서 CPU 한도 4를 유지했다.

실제 입력 토큰은 127,177개이며 패딩 포함 토큰 수는 단순 배치 16보다 44.2% 감소했다. 짧은 배치의 관측 최소 채움률은 85%, OOM은 0이었다. GPU의 불필요한 계산과 대기가 줄면 사용률도 내려갈 수 있다. 이번 GPU 평균 하락만으로 성능 악화를 판단해서는 안 된다. 전체 속도와 유효 처리량을 함께 판단해야 하며 평균 사용률 80% 목표는 달성하지 못했다.

같은 14문서, 885벡터를 사용했다. manifest SHA-256은 `d9e75e20b8c19560deadc125fd42299dd5b6bfc8997b89aadf6549f16388846f`다. 서비스 요청 52개가 모두 성공했고 입력 913개에는 제목 등의 추가 입력이 포함된다. 전체 시간은 첫 호스트 문서 시작부터 마지막 정리·ACK 완료까지이며 GPU 표본도 이 구간에 맞췄다.

## 남은 지연: 겹치는 청킹·색인 구간

PPTX 한 건의 청킹 구간이 8.649초, 다른 XLSX 한 건의 색인 구간이 8.880초였다. 두 구간은 같은 API 프로세스에서 8.607초 겹쳤고 종료 시각 차이는 0.042초였다. 청킹 구간에 해당하는 GPU 표본 41개 중 37개가 사용률 0%, 평균은 8.9%였다. GPU 구간 대응은 감사 기록의 UTC와 단조 시계 간 근사 매핑이다.

이는 GPU 밖에서 작업 진행이 지연됐다는 증거다. 두 작업이 동시에 느려진 공통 원인이 의심되지만, 현재 기록으로 그 원인을 확정할 수는 없다. 특히 8.65초와 8.88초를 더해서 약 17.5초를 낭비했다고 해석하면 안 된다.

코드 확인 결과 `chunk_service.py`의 청킹 계측은 `await asyncio.to_thread(OfficeChunker().chunk, ...)` 전체를 감싼다. 따라서 계산뿐 아니라 실행 대기와 이벤트 루프 복귀 지연도 포함한다. 색인 계측은 DB 조회, 문서 저장소 삽입, 체크포인트 갱신과 refresh 등을 포함한다. 저장소 호출의 `thread_pool_exec`는 호출마다 별도 실행기를 사용하므로 두 단계가 동일한 단일 스레드 큐에서 막혔다고 단정할 근거도 없다.

다음 원인 분리에 필요한 것은 이벤트 루프 지연, 작업 제출→실행 시작→실행 종료, 스레드 CPU 시간, DB/색인 요청별 응답 시간이다. 이번에는 해당 추가 계측이나 새 성능 실험을 진행하지 않았다. CPU 파서를 더 늘리거나 GPU 배치를 다시 키울 근거로 이 지연을 사용하지 않는다.

## 검증과 한계

후보 실측은 요청대로 1회다. 첫 워밍업에서는 13문서 성공, 1문서 HOST_WORKER_ERROR가 발생해 제외했다. 원인은 미확정이며 재시도 워밍업과 실측에서는 모두 14문서/885벡터가 성공했다. 기존 배치 8과 16 결과를 재사용했고 같은 시각에 재측정하지 않았다. 기존 배치 8에는 상세 GPU 계측도 없으므로 단회 차이 전체를 배치 정책의 인과 효과로 확정하지 않는다.

CUDA 이벤트는 순수 커널 활성 시간만이 아니라 스트림 경과 시간을 측정한다. 요청 대기, 결과 복사 대기, CUDA 이벤트와 문서별 단계 시간은 서로 겹쳐 합산할 수 없다. GPU 사용률은 장치 전체 표본이다.

집중 테스트 16개가 통과했다. 독립 읽기 전용 리뷰에서 중요한 결함은 없었다. 정확히 85%인 경계와 기능 활성화 상태의 중간/긴 입력 경계에 대한 추가 테스트는 보류했다. OOM 분할 재시도에서는 자식 배치가 85% 미만일 수 있으므로 실제 채움률을 확인해야 한다. 이번 실행에서는 OOM이 없었다.

기존 벡터 885개와 비교한 최소 코사인 유사도는 0.9999999999969806, 최대 성분 차이는 3.05e-7이었다. 파서 CPU 제한 대기는 합계 0.013초, VM 최소 가용 메모리는 약 2,252 MiB, 컨테이너 OOM은 없었다. 이 수치만으로 순간적인 CPU·메모리·I/O 경합을 배제하지는 않는다.

원본 14개의 해시·크기·수정 시각이 유지됐고 host/API/parser 임시 작업 파일은 0개다. 시험 컨테이너와 DB를 제거하고 후보 포트를 해제했다. 원래 GPU/API HTTP 200과 GTE/ingest/watcher 예약 작업 Running을 확인했다. 운영 서비스 코드와 기본값은 변경하지 않았다. 공유 가능한 수치는 [측정 JSON](measurements/gpu-bucket85-2026-10-13.json)에 저장했다.
