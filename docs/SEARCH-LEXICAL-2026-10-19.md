# 문서 검색 제목·한국어·식별자 보강 (2026-10-19)

누락됐던 제목 색인과 범용 키워드 보강을 구현하고, 기존 검색 가능 청크 12,553개에 적용했다. 기존 서비스 이미지에서 변경한 Python 파일은 5개이며 새 버전의 로컬 배포와 공개 경로 연결을 확인했다. 특정 제품 사전, 동의어 목록, 질문별 예외는 추가하지 않았다.

## 구현과 유지한 계약

- 파서가 파일명의 마지막 확장자를 제외한 제목을 `title_tks`, `title_sm_tks`에 기록한다.
- 제목과 본문에 보조 색인 4개를 추가한다. 한국어는 공백을 제거한 연속 한글의 2·3글자 조각으로 띄어쓰기와 조사 차이를 보완한다. ASCII 식별자는 NFKC·소문자 정규화 후 기호·숫자를 보존한 토큰으로 저장한다. 예를 들어 C++/C#, MES/ME, 모델 번호를 서로 구별한다. 이 예들은 규칙 검증용이며 제품별 분기가 아니다.
- 기존 BM25 표현과 보조 표현을 같은 검색 범위 안에서 `dis_max`로 결합한다. 별도 검색 레인이나 결과 후처리를 추가하지 않았다. 긴 질의는 보조 ASCII 토큰 64개, 한글 조각 128개로 제한한다.
- BM25 128 / dense 128 → 동일 가중 RRF(k=60) → 문서별 최대 8개·전체 최대 128개 → Jina v3.5 → 최종 5개를 유지했다. GTE multilingual base 768차원, dense k=2048/num_candidates=4096, 청킹, 인증, 문서 범위, 원본 버전 검증도 유지했다.
- 재정렬 입력은 기존대로 **본문 앞 2,400자**다. 제목을 재정렬 입력에 붙이지 않았다.

## 평가 방법과 한계

- 합성 문서 30개에서 정답이 정해진 질문 24개를 구성했다. 실제 Elasticsearch, GTE, Jina를 사용했다. 두 군의 합성 문서·질의 벡터는 같은 캐시를 사용했다. 합성 문서 벡터는 제목 0.1 + 본문 0.9이며, 이 통제 코퍼스는 실제 수집 파이프라인 전체를 재현하는 시험은 아니다.
- 실제 제목은 결과를 보기 전에 제목 해시 순서로 12개를 선택했다. 절반은 연속 한글 사이 공백을 제거했다. 정답은 같은 파일명 stem을 가진 문서 집합으로 고정했다. 실제 검색 서비스의 전체 검색 범위를 사용했다. 제목 탐색 시험이며 임의의 내용 질문에 대한 사람의 관련성 판정은 아니다.
- 두 군의 manifest, 원본 카탈로그 버전, 합성 벡터 캐시, 후보·재정렬 계약이 일치함을 확인했다. 일시적 제공자 오류는 재시도했으며 실패를 오답으로 집계하지 않았다.
- 네트워크·모델 준비 시간의 변동이 있어 이번 실행으로 지연 시간 개선을 주장하지 않는다. 더 넓은 독립 질의와 사용자 판정은 별도 검증이 필요하다.

## 재실행과 복구 자료

`tools/evaluate_docmind_lexical.py`를 각 이미지의 동일 설정 환경에서 `--arm baseline|candidate --live --cache <private-cache> --checkpoint <separate-private-checkpoint>`로 실행한다. baseline은 보강 전 색인·코드, candidate는 보강 후 색인·코드가 필요하다. 결과 JSON의 manifest와 카탈로그·벡터 해시를 대조한다. 실제 코드가 보강된 상태에서 `--arm baseline`만 지정하면 원래 서비스로 되돌아가는 것은 아니다.

`tools/backfill_docmind_search_fields.py --journal <private-journal>`은 사전 조회이며, `--apply`가 실제 적용, `--verify`가 보호 필드 해시 확인, `--rollback`이 추가 필드의 이전 값 복원이다. 업데이트와 복원은 Elasticsearch sequence/primary-term 조건으로 동시 변경 덮어쓰기를 막는다. ACK를 받은 적용 레코드만 복원하므로 통신 중단으로 결과가 불확실한 intent는 별도 대조가 필요하다. journal에는 파생 텍스트가 들어가므로 Git 밖에 보관한다.
