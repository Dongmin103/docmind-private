# GPU 입력 공급과 API 대기 진단: 실측 1회

동일 14문서의 처리 구간은 **20.60초**, GPU 평균은 **51.6%**였다. 직전 길이별 배치 실험의 28.85초보다 28.6%, 이전 최선 배치 8의 22.93초보다 10.2% 짧았다. 다만 본문 처리 완료 이후 시험 제어기의 상태 확인이 지연돼, 실행 시작부터 완료를 관측하기까지는 **41.87초**였다. 문서 처리 시간과 이 제어기 시간을 구분해야 한다.

## 변경과 확인된 원인

첫 진단 워밍업에서 호스트 요청의 인증 함수가 비동기 API 경로에서 동기 DB 트랜잭션을 실행하는 것을 관측했다. API 루프 지연 표본에는 `docmind_worker_auth.verify → database.atomic → begin` 호출이 있었고, 이 워밍업의 관측 최대 루프 지연은 약 1.11초였다. 이는 실제 차단 경로지만, 이전 실험의 청킹·색인 8.6초 지연 원인이라고 확정하지 않는다.

`_authenticate_worker`는 요청의 서명 관련 값을 먼저 캡처하고 `asyncio.to_thread`로 검증을 수행하도록 변경했다. 검증 함수와 nonce 트랜잭션은 유지했다. 잘못된 인증이 DB 연결을 먼저 획득하지 않도록 연결은 기존 검증 내부에서 지연 개방하고, 성공·실패 모두 동일 작업 스레드의 `finally`에서 닫는다. 독립 리뷰에서 발견한 선행 연결 획득 문제를 이 방식으로 수정하고 재검토했다.

계측은 시험 API에만 설치했다. executor 제출→실행 시작 대기, 실행 경과·스레드 CPU 시간, DB/색인 호출 시간, API 및 문서별 이벤트 루프 지연을 기록한다. 지연 중 호출 위치는 파일명·함수명·줄 번호만 저장한다. 문서 내용, 함수 인수·결과, SQL, 예외 메시지, 지역 변수는 기록하지 않는다. 이벤트 큐는 8,192개로 제한하고 유실/기록 오류를 확인한다.

## 남은 병목과 해석

- 청킹 실행 합계 0.383초, 단일 작업 최대 0.104초, 스레드 CPU 합계 0.311초였다. 최대 executor 대기는 0.016초였다. 이번 관측에서는 청킹 스레드 수 부족의 근거가 없다.
- 색인 삽입 최대 0.091초, refresh 최대 0.020초였다. 이전의 8.6초 청킹·색인 지연은 재현되지 않았다.
- 인증 작업 최대 0.050초, executor 대기 최대 0.00083초였다. 인증은 작업 스레드에서 실행됐다.
- GPU 토큰화 합계 0.277초, 추론 슬롯 대기 합계 9.218초, CUDA 이벤트 합계 10.655초였다. 토큰화는 큰 비중이 아니었다.
- 임베딩 요청 실행 구간 합계는 약 11.26초였다. 가장 긴 서비스 실행 공백은 약 1.61초였다. 여러 작은 공백과 준비·마무리 시간이 남아 평균 GPU 80%에는 도달하지 못했다.
- 문서별 루프에서 동기 HTTP 응답 대기, DB 재시도 위치, 검색용 토큰화 호출이 관측됐다. 이들은 추가 조사 후보이며 이번 수정에 함께 포함하지 않았다.

API 이벤트는 동일 프로세스의 단조 시계와 감사 구간으로 맞췄다. API와 Windows 시계는 시험 직전 약 0.41초 차이가 있어 두 환경의 UTC만 직접 비교하지 않는다. CUDA 이벤트는 순수 커널 활성 시간만이 아니며, 단계 합계와 대기 시간은 중첩돼 더할 수 없다.

## 검증·제약·복구

본 실측은 **1회**이고 이전 두 기준선은 재사용했다. 진단 워밍업 후 API 재시작에 따른 준비 실행을 수행했다. 첫 재시작 뒤 준비 실행은 클라이언트 동시성이 초기값 1로 돌아간 상태였으므로 비교에서 제외했다. 최종 준비와 본 실측에는 2로 복구했다. 추가 준비 실행은 성능 개선 근거로 사용하지 않았다.

상세 계측 추가, 서로 다른 실행 시각, 재현되지 않은 과거 지연 때문에 28.6% 또는 10.2% 개선 전체를 인증 수정의 인과 효과로 확정하지 않는다. 읽기 전용 저장소 제거 검사도 시험 진행과 겹쳤으며 호스트 CPU/I/O 간섭 여부를 따로 측정하지 못했다. 추가 실측은 수행하지 않았다. 첫 진단의 루프 계측은 API 메인 루프만, 최종 계측은 문서별 루프도 포함하므로 지연 표본 개수끼리는 직접 비교하지 않는다.

인증·API 테스트 30개, GPU/계측 테스트 20개가 통과했다. 기존 코드에서 이벤트 루프 차단 회귀 테스트의 실패를 먼저 확인했다. 제거된 런타임 참조 검사도 통과했다. 독립 리뷰의 중요한 지적은 수정 후 해결 확인을 받았다.

885벡터를 기존 벡터와 비교한 최소 코사인 유사도는 0.9999999999969806이다. 파서 CPU 제한 대기 0초, VM 최소 가용 메모리 약 2,324 MiB, API 최대 메모리 약 1,759 MiB, GPU 및 컨테이너 OOM 0이었다. 원본 14개는 해시·크기·수정 시각이 유지됐다. 임시 작업 파일, 시험 컨테이너, 시험 DB와 GPU 후보 포트를 정리했다. 원래 GPU/API HTTP 200과 GTE/ingest/watcher 예약 작업 Running을 확인했다.

변경은 개발 작업 트리에만 남겨 운영 배포하지 않았다. 새 CPU 파서 증가나 별도 준비 큐도 도입하지 않았다. 다음 판단에서는 완료 확인 지연을 먼저 분리하고, 확인된 GPU 입력 공백에만 제한된 선행 준비를 적용해야 한다. 수치는 [측정 JSON](measurements/gpu-feed-2026-10-13.json)에 저장했다.
